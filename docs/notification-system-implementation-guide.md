## 1. 背景与目标

### 1.1 为什么需要消息通知

进步局的核心是「每日行动 + 长期目标 + 小队同行 + AI 教练」。用户离开小程序后，能否被及时唤回，决定了留存与目标完成率。微信订阅消息是当前小程序**唯一合规的主动触达通道**，承担以下产品价值：

- **召回**：每日行动提醒，让用户回到小程序完成今日任务
- **反馈**：AI 教练每日建议、复盘结果触达
- **社交驱动**：小队成员完成行动、连续达成等事件，激发同伴效应
- **里程碑**：周/月/年复盘节点提醒

### 1.2 设计原则

依据 `AGENTS.md` 第 5、8、11 节，本系统遵循以下原则：

| 原则 | 说明 |
|---|---|
| 真实触发 | 通知内容必须来自真实业务事件，禁止营销骚扰 |
| 用户主权 | 用户可随时查看授权状态、退订、调整偏好 |
| 克制频率 | 不滥用「打扰度」，单日单用户触达有上限 |
| 隐私合规 | 与现有 `pages/privacy-center` 联动，纳入隐私协议 |
| 一致命名 | 全项目统一称「消息通知」，不与「推送/提醒/模板消息」混用 |
| 闭环兜底 | 通知失败或未授权时，必须有站内消息兜底，不丢业务事件 |

### 1.3 不做的事

- ❌ 不引入「服务通知 + 订阅消息」双轨并行（本项目非电商交易类，无必要）
- ❌ 不申请长期订阅（进步局属于个人成长类目，无长期订阅资质）
- ❌ 不为「拉新」发送通知，仅在用户已发生业务行为后触发
- ❌ 不在用户首次进入小程序时立即弹订阅授权

## 2. 微信订阅消息机制回顾

### 2.1 两类订阅

| 类型 | 用户授权次数 | 可发送次数 | 适用类目 | 本项目是否可用 |
|---|---|---|---|---|
| 一次性订阅 | 每次授权 1 个模板 | 授权 1 次 → 发 1 条 | 全类目 | ✅ 全部场景使用 |
| 长期订阅 | 授权 1 次 | 多次（有频次限制） | 仅民生/政务/医疗/交通/金融/新闻等公共服务 | ❌ 不申请 |

**结论**：本项目所有通知均采用「一次性订阅」机制。

### 2.2 一次性订阅的核心规则

1. **授权与发送一一对应**：用户在小程序内点击「允许」一次，开发者只能发一条对应模板的消息
2. **授权有时效**：通常授权后需在合理时间内（平台建议 24 小时内）下发，超时授权可能失效
3. **可在业务流中累积授权**：用户完成一次行动可同时授权「明日提醒」「小队动态」「周复盘」3 个模板，单次弹窗最多 3 个
4. **用户可勾选「总是保持以上选择」**：勾选后该模板不再弹窗，按上次选择自动处理
5. **授权记录在微信侧**：开发者无法查询某用户是否已授权（只能查询发送结果），需自建授权账本

### 2.3 模板消息（已废弃，仅作了解）

2020 年已下线，本项目**禁止**任何模板消息残留代码或文档引用。

### 3.1 关键架构事实

经项目代码勘察，确认以下事实：

|---|---|

| 服务层目录 | `miniprogram/services/*.ts`（已有 21 个服务文件） |
| 工具层目录 | `miniprogram/utils/` |
| 隐私中心 | 已有 `pages/privacy-center` |
| 现有通知代码 | **无**（白纸状态） |

### 3.2 选型决策：云开发模式（推荐）

微信订阅消息发送有两条技术路径：

| 路径 | access_token 管理 | 调用方式 | 与本项目契合度 |
|---|---|---|---|
| A. 云开发模式 | 云开发自动管理，无需手动获取 | 云函数内调用 `cloud.openapi.subscribeMessage.send` | ✅ **推荐** |
| B. 传统 HTTPS 模式 | 需自行获取/缓存/刷新 | 调用 `api.weixin.qq.com/cgi-bin/message/subscribe/send` | ❌ 不采用 |

**选择路径 A 的理由**：

1. 本项目已全面使用云开发，所有业务通过云函数承载
2. 云开发模式**无需管理 access_token**，省去一整套缓存、刷新、并发竞争逻辑
3. 云函数天然具备触发器（定时器）、数据库监听等能力，与通知触发场景天然契合
4. 与现有 `generatePlan` 云函数 + action 路由的范式完全一致
5. 权限边界清晰：发送权限在云函数侧，前端无法绕过业务校验直接发送

## 4. 通知场景设计

### 4.1 场景总表

基于 `AGENTS.md` 第 4、5 节业务架构，识别出 6 个核心通知场景：

| # | 场景 | 触发时机 | 模板类型 | 关键词建议 |
|---|---|---|---|---|
| N1 | 每日行动提醒 | 每日固定时间（如早 8 点）由定时触发器检查 | 一次性 | 日期、今日行动摘要、目标名称、跳转 |
| N2 | AI 教练每日建议 | AI 教练生成完今日建议后 | 一次性 | 日期、建议摘要、目标名称、跳转 |
| N3 | 小队成员完成行动 | 小队成员完成行动事件 | 一次性 | 成员昵称、行动名称、小队名称、跳转 |
| N4 | 周复盘提醒 | 每周固定时间（如周日晚 8 点） | 一次性 | 周期、本周完成数、累计投入、跳转 |
| N5 | 阶段目标达成 | 用户完成阶段目标时 | 一次性 | 目标名称、阶段名、完成时间、跳转 |
| N6 | 邀请加入小队 | 用户被邀请后（可选，MVP 不做） | 一次性 | 邀请人、小队名称、房间号、跳转 |

### 4.2 MVP 阶段建议

**MVP 只做 N1 + N2 + N3**，理由：

- N1（每日行动提醒）：最高召回价值，验证整个链路
- N2（AI 教练建议）：与产品差异化能力绑定，强化 AI 教练心智
- N3（小队成员完成）：激活小队社交，符合「共同坚持」产品定位

N4、N5 在 V1.1 迭代，N6 视数据再决定。

### 4.3 每个场景的详细设计

#### 场景 N1：每日行动提醒

| 项 | 设计 |
|---|---|
| 触发主体 | 云函数定时触发器（每日 08:00） |
| 触发条件 | 用户在前一天 22:00 前完成订阅授权，且今日有 ≥1 个未完成行动 |
| 模板标题 | 今日行动提醒 |
| 关键词 | `日期` / `今日行动数` / `目标名称` / `提示语` |
| 跳转目标 | `pages/index/index`（今日页） |
| 授权时机 | 用户在前一天完成行动后，弹窗询问「是否提醒你明天的行动」 |
| 限制 | 单用户单日 1 条；用户当日已主动打开小程序则不发送（可选优化） |

#### 场景 N2：AI 教练每日建议

| 项 | 设计 |
|---|---|
| 触发主体 | AI 教练服务生成建议后异步触发 |
| 触发条件 | 用户已订阅，且 AI 教练今日生成了非空建议 |
| 模板标题 | AI 教练每日建议 |
| 关键词 | `日期` / `建议摘要` / `目标名称` / `查看详情` |
| 跳转目标 | `pages/daily-coach/index`（AI 教练页） |
| 授权时机 | 用户在 AI 教练页查看建议后，弹窗「明天也为你生成建议并提醒你？」 |
| 限制 | 建议摘要 ≤ 20 字符；单用户单日 1 条 |

#### 场景 N3：小队成员完成行动

| 项 | 设计 |
|---|---|
| 触发主体 | 成员完成行动的云函数 action 内联触发 |
| 触发条件 | 同小队其他成员已订阅「小队动态」 |
| 模板标题 | 小队动态提醒 |
| 关键词 | `成员昵称` / `行动名称` / `小队名称` / `时间` |
| 跳转目标 | `pages/team-activity/index`（小队动态页） |
| 授权时机 | 用户进入小队页后，引导「关注小队动态」 |
| 限制 | 单用户单日接收上限 5 条；避免连击刷屏（同一成员 30 分钟内只通知 1 次） |

## 5. 完整实施流程

### 5.1 总览：六步实施

```
Step 1  微信公众平台申请模板
   ↓
Step 2  前端封装订阅授权服务（services/notification.ts）
   ↓
Step 3  云函数侧新增发送能力（generatePlan action + notificationScheduler）
   ↓
Step 4  业务触发点埋入授权弹窗与发送调用
   ↓
Step 5  隐私中心改造：通知偏好设置入口
   ↓
Step 6  测试与灰度
```

### 5.2 Step 1：申请模板

**操作位置**：[微信公众平台](https://mp.weixin.qq.com) → 订阅消息 → 我的模板 → 从公共模板库选用或申请新模板

**申请清单**（MVP 3 个模板）：

| 模板用途 | 建议从公共库选用类目 | 关键词顺序 |
|---|---|---|
| 每日行动提醒 | 个人信息收集类 / 提醒类 | 日期、内容、名称、备注 |
| AI 教练建议 | 服务通知类 | 日期、内容、名称、备注 |
| 小队动态 | 社交通知类 | 名称、内容、名称、时间 |

**注意事项**：

- 类目必须与小程序已通过审核的服务类目一致（进步局注册时是什么类目，需到小程序后台核对）
- 关键词**顺序固定**，申请通过后不可调整
- 关键词有类型约束（如「时间」类型必须填日期格式）
- 申请审核通常 1-3 个工作日
- 模板 ID 形如 `xXxXxXxXxXxXxXxXxXxXxXxXxXxXxXxXxXxXx`，需记录到配置文件

**配置文件规划**：

```
miniprogram/config/
└── notification.ts   # 【新增】集中管理模板 ID、场景映射
```

模板 ID 属于非敏感信息，可硬编码在小程序端；但发送逻辑必须全部在云函数侧。

### 5.3 Step 2：前端订阅授权服务

#### 5.3.1 设计要点

参考 `services/team.ts` 的范式，新建 `services/notification.ts`，统一封装：

1. **授权请求**：封装 `wx.requestSubscribeMessage`，处理「总是保持以上选择」「拒绝」「失败」三种结果
2. **授权账本同步**：每次授权结果上报云函数，写入 `subscription_ledger` 集合
3. **偏好读取**：从云函数拉取用户当前可发送的模板列表（用于隐私中心展示）
4. **退订**：用户在隐私中心可主动退订某类通知

#### 5.3.2 关键设计决策

**授权账本必须存在云端**，原因：

- 微信侧不提供「查询用户是否已授权」的接口
- 必须自建账本记录「用户授权了几个额度」，发送时扣减
- 账本写在云数据库集合，前端只读

**前端授权流程**：

```
用户完成业务动作（如完成今日行动）
  ↓
判断是否合适弹授权（用户当日内未弹过 + 业务时机合适）
  ↓
调 wx.requestSubscribeMessage({ tmplIds: [...] })
  ↓
回调返回每个模板的 accept / reject / ban 状态
  ↓
将 accept 的模板上报云函数：action=notification.subscribe
  ↓
云函数写入 subscription_ledger：{ openid, templateId, scene, quota: 1, expireAt }
```

**「ban」状态特殊处理**：

- `ban` 表示用户已选「总是保持以上选择：拒绝」，且无法再弹窗
- 此时前端**禁止再次调用** `wx.requestSubscribeMessage`，否则会报错
- 需引导用户去微信设置中开启（路径：微信 → 我 → 设置 → 隐私 → 订阅消息授权）
- 在隐私中心展示 ban 状态，并提供引导文案

#### 5.3.3 授权时机规范

依据 `AGENTS.md` 第 5.3 节和微信平台规范，**禁止**以下时机弹授权：

- ❌ 小程序首次启动
- ❌ 用户未进行任何业务操作时
- ❌ 弹窗广告位、引导页
- ❌ 同一模板 24 小时内重复弹窗（即使用户曾拒绝）

**推荐**时机：

| 场景 | 推荐弹窗时机 | 文案示例 |
|---|---|---|
| N1 每日行动提醒 | 用户完成今日最后一项行动后 | 「明天继续？授权后我会在早上提醒你今天的行动安排」 |
| N2 AI 教练建议 | 用户首次查看 AI 教练建议后 | 「明天也为你生成建议并提醒？授权后不会错过」 |
| N3 小队动态 | 用户加入小队或进入小队页 30 秒后 | 「关注小队伙伴的动态？授权后第一时间通知你」 |

### 5.4 Step 3：云函数侧发送能力

#### 5.4.1 架构选型

采用「**统一入口 + 独立调度器**」混合模式：

```
┌─────────────────────────────────────────────────────────────┐
│  generatePlan 云函数（已有）                                  │
│  ├── action=notification.subscribe   接收前端授权上报         │
│  ├── action=notification.unsubscribe 处理用户退订             │
│  ├── action=notification.preference  返回用户偏好             │
│  └── action=notification.send        业务事件内联发送         │
│       （如小队成员完成行动时，由 action=team.completeAction 触发）│
└─────────────────────────────────────────────────────────────┘
                            ↑
                            │
┌─────────────────────────────────────────────────────────────┐
│  notificationScheduler 云函数（新增）                         │
│  ├── 定时触发器：每日 08:00  → 扫描 ledger → 发送 N1          │
│  └── 定时触发器：每周日 20:00 → 扫描 ledger → 发送 N4（V1.1） │
└─────────────────────────────────────────────────────────────┘
```

**为什么不全塞进 generatePlan？**

- 定时触发器需要独立云函数承载
- 通知调度逻辑较重，独立函数便于独立监控、限流、降级

**为什么不完全独立？**

- 内联触发（如小队完成行动 → 通知队友）必须与业务 action 在同一事务上下文
- 单独发请求会引入额外网络开销与一致性问题

#### 5.4.2 发送实现要点

云函数内调用微信开放接口：

```
cloud.openapi.subscribeMessage.send({
  touser: openid,
  templateId,
  page,                       // 跳转小程序页面路径
  miniprogramState,           // develop / trial / release
  lang: 'zh_CN',
  data: {                     // 按模板关键词顺序填充
    thing1: { value: '...' },
    number2: { value: '...' },
    date3: { value: '...' },
  }
})
```

**关键约束**：

- 必须在云函数内调用，**前端无法直接调用**
- `data` 字段名（如 `thing1`、`number2`）由模板审核通过后固定，不可改
- 单字段值有长度限制（thing ≤ 20 字符，character_string ≤ 32 字符）
- `miniprogramState` 三态：开发版 / 体验版 / 正式版，按部署环境切换
- 调用频率受云开发配额限制（默认 100 万次/天，足够）

#### 5.4.3 发送流程（统一封装）

每个发送动作的内部流程：

```
1. 查询 subscription_ledger：该用户该模板是否有可用 quota
   ├── 无 quota → 跳过，记日志（不报错）
   └── 有 quota → 继续
2. 查询 notification_preference：用户是否退订了该场景
   ├── 已退订 → 跳过
   └── 未退订 → 继续
3. 查询 notification_sent_log：今日是否已发过该场景
   ├── 已发且场景有日限 → 跳过
   └── 未达上限 → 继续
4. 构造 data，调用 cloud.openapi.subscribeMessage.send
5. 处理返回：
   ├── 成功 → 扣减 ledger quota，写 sent_log
   ├── errcode=43101（用户未订阅）→ 标记 ledger 失效，不重试
   ├── errcode=47003（模板审核不准）→ 告警，停止该模板发送
   └── 其他错误 → 写入重试队列，指数退避重试 3 次
```

### 5.5 Step 4：业务触发点埋入

#### 5.5.1 授权触发点（前端）

| 触发点 | 文件位置 | 推荐授权模板 |
|---|---|---|
| 完成今日最后一项行动 | `services/checkin.ts` 或对应 action 回调 | N1 |
| 查看 AI 教练建议 | `pages/daily-coach/index` | N2 |
| 加入小队成功 | `services/team.ts` 的 `joinRoom` | N3 |
| 进入小队页停留 ≥ 30 秒 | `pages/team/index` 的 onShow | N3 |

**埋入原则**：复用现有 service 方法的回调链，不新建独立调用入口。

#### 5.5.2 发送触发点（云函数侧）

| 场景 | 触发位置 | 调用方式 |
|---|---|---|
| N1 每日提醒 | `notificationScheduler` 定时触发器 | 扫描 ledger 批量发送 |
| N2 AI 教练建议 | `generatePlan` action=dailyCoach.generate | 生成建议后内联调用 send |
| N3 小队成员完成 | `generatePlan` action=team.completeAction | 完成行动后遍历队友 send |

**关键**：N3 这类「事件驱动」场景，**发送失败不能阻塞业务主流程**。必须用 `Promise.allSettled` 或 try-catch 隔离，发送失败只记日志，不影响行动完成结果。

### 5.6 Step 5：隐私中心改造

#### 5.6.1 新增入口

在 `pages/privacy-center/index` 新增分组「消息通知」，包含：

| 子项 | 类型 | 说明 |
|---|---|---|
| 每日行动提醒 | Switch | 控制 N1 |
| AI 教练建议 | Switch | 控制 N2 |
| 小队动态 | Switch | 控制 N3 |
| 周复盘提醒 | Switch | 控制 N4（V1.1） |
| 微信订阅管理 | 跳转按钮 | 跳转 `wx.openSetting` 引导用户管理微信侧授权 |

#### 5.6.2 偏好数据流

```
隐私中心切换 Switch
  ↓
调用 action=notification.updatePreference
  ↓
更新 notification_preference 集合：{ openid, scene, enabled }
  ↓
返回成功，前端 Switch 状态更新
```

**注意**：偏好关闭**不会**取消微信侧的订阅授权，只是云函数发送时跳过。用户下次授权仍需走微信原生弹窗。这一点必须在隐私中心用文案说明：「关闭后不再收到此类通知；如需重新开启，请在该场景出现时再次授权」。

## 6. 数据模型设计

### 6.1 云数据库集合规划

新增 3 个集合，全部存于云开发数据库：

```
cloud database
├── subscription_ledger        # 授权账本
├── notification_preference    # 用户偏好
└── notification_sent_log      # 发送日志
```

### 6.2 集合字段定义

#### 6.2.1 subscription_ledger（授权账本）

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 自动生成 |
| `_openid` | string | 用户 openid（云开发自动写入） |
| `templateId` | string | 微信模板 ID |
| `scene` | string | 业务场景标识（如 `daily_action_reminder`） |
| `quota` | number | 剩余可发送次数（一次性订阅初始为 1） |
| `status` | string | active / consumed / expired / banned |
| `authorizedAt` | date | 授权时间 |
| `expireAt` | date | 过期时间（建议授权后 +7 天） |
| `consumedAt` | date \| null | 已发送时间 |
| `clientScene` | string | 授权时所在的业务页面（用于分析转化率） |

**索引建议**：
- 组合索引：`(_openid, scene, status)` —— 发送时查询主力索引
- 单字段索引：`expireAt` —— 定时清理过期记录

#### 6.2.2 notification_preference（用户偏好）

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 自动生成 |
| `_openid` | string | 用户 openid |
| `scenes` | object | `{ daily_action_reminder: true, ai_coach_advice: true, team_activity: false }` |
| `updatedAt` | date | 最后更新时间 |

**索引建议**：主键 `_openid` 唯一。

#### 6.2.3 notification_sent_log（发送日志）

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 自动生成 |
| `_openid` | string | 接收者 openid |
| `scene` | string | 业务场景 |
| `templateId` | string | 模板 ID |
| `status` | string | success / failed / skipped |
| `errcode` | number \| null | 微信返回的错误码 |
| `errmsg` | string \| null | 错误描述（≤ 200 字符） |
| `sentAt` | date | 发送时间 |
| `requestId` | string | 关联业务事件 ID（如 action ID） |

**索引建议**：
- 组合索引：`(_openid, scene, sentAt)` —— 日限检查
- 单字段索引：`sentAt` —— 按时间范围清理

### 6.3 数据安全规则

所有集合**必须配置云数据库安全规则**：

| 集合 | 读权限 | 写权限 |
|---|---|---|
| subscription_ledger | 仅创建者（_openid 匹配） | 仅云函数（拒绝前端直接写） |
| notification_preference | 仅创建者 | 仅云函数 |
| notification_sent_log | 仅创建者可读自己的记录 | 仅云函数 |

**关键**：前端**不能**直接写 ledger，所有授权记录必须通过云函数 action 上报，由云函数校验后写入。否则用户可伪造授权额度。

## 7. 错误处理与降级方案

### 7.1 常见错误码处理

| errcode | 含义 | 处理策略 |
|---|---|---|
| 0 | 成功 | 扣减 quota，写 sent_log |
| 43101 | 用户拒绝接收消息（或未订阅） | 标记 ledger quota=0，不重试 |
| 47003 | 模板参数不准确 | 告警，暂停该模板发送，人工排查 |
| 40037 | 订阅模板 id 不正确 | 告警，检查配置 |
| 41030 | 页面路径错误 | 告警，检查 page 参数 |
| 45009 | 调用频率限制 | 指数退避重试 3 次 |
| -1 | 系统繁忙 | 重试 3 次，间隔 2/4/8 秒 |

### 7.2 降级机制

#### 7.2.1 站内消息兜底

云函数发送失败时，**同时写入 `in_app_messages` 集合**（如已有则复用，无则新增），用户下次进入小程序时在「今日页」顶部展示未读站内消息。

**理由**：业务事件（如小队成员完成行动）必须让用户感知到，不能因微信侧发送失败而丢失。

#### 7.2.2 触发器失败兜底

`notificationScheduler` 定时触发器执行失败时：

- 云函数日志记录失败原因
- 下次触发时补发当日漏发的用户（仅补发当日，不跨日）
- 连续 3 天失败触发告警

#### 7.2.3 配额耗尽降级

`subscription_ledger` quota 为 0 时：

- 不发送，不报错
- 在用户下次进入小程序相关页面时，**温和引导**重新授权
- 引导文案：「你的提醒服务已到期，点击续订」，不要用「重新授权」等技术词

### 7.3 防骚扰机制

| 机制 | 规则 |
|---|---|
| 单用户单场景日限 | N1/N2 各 1 条/天；N3 ≤ 5 条/天 |
| 全局日限 | 单用户所有场景合计 ≤ 7 条/天 |
| 静默时段 | 22:00 - 08:00 不发送（除用户主动设置的预约提醒） |
| 频次熔断 | 同一用户 30 分钟内 ≤ 2 条 |
| 用户反馈熔断 | 用户在隐私中心反馈「太多」时，自动降低 N3 频次 |

## 8. 合规与审核

### 8.1 隐私协议联动

依据 `AGENTS.md` 第 5.3、11 节和已有的 `pages/privacy-center`：

1. **更新隐私政策**：在 `pages/legal/privacy` 中新增「消息通知」章节，说明：
   - 收集的授权信息（openid、授权场景、授权时间）
   - 信息用途（仅用于发送用户订阅的通知）
   - 不收集的内容（不读取聊天记录、不获取位置等）
   - 退订方式

2. **首次授权前置**：用户首次同意订阅前，必须在隐私中心或弹窗旁有可点击的「了解通知服务说明」入口

3. **隐私接口声明**：在 `app.json` 的 `requiredPrivateInfos` 中**不需要**新增任何项（订阅消息不属于敏感接口），但需在 `privacy.json` 中登记订阅消息用途

### 8.2 模板内容合规

| 规则 | 说明 |
|---|---|
| 真实性 | 关键词值必须真实反映业务状态，禁止「您有一条新消息」等诱导性话术 |
| 不诱导跳转 | 不使用「点击查看惊喜」「立即领取」等违规文案 |
| 不营销 | N1-N5 均为业务通知，禁止塞入广告或活动推广 |
| 字段长度 | 严格按模板类型限制（thing ≤ 20 字符） |

### 8.3 审核常见拒审原因预防

| 风险点 | 预防措施 |
|---|---|
| 诱导订阅 | 授权弹窗不在首屏，不与利益挂钩（如「授权送积分」禁止） |
| 模板与类目不符 | 申模板时核对小程序服务类目 |
| 频次过高 | 实施防骚扰机制（见 7.3） |
| 无法退订 | 隐私中心提供退订入口（见 5.6） |
| 内容与模板不符 | 发送前严格按模板字段类型校验 |

### 8.4 与 `AGENTS.md` 第 10 节对齐

- ✅ 不输出 openid 到日志（错误日志中 openid 脱敏）
- ✅ 请求过程避免重复提交（已通过 ledger quota 原子扣减保证）
- ✅ 乐观更新具备失败回滚（发送失败时 quota 不扣减）
- ✅ 用户退出小队时关联处理：N3 自动停止（在 preference 中标记）

## 9. 测试与验证

### 9.1 测试矩阵

| 测试维度 | 测试点 | 验证方法 |
|---|---|---|
| 授权流程 | 首次授权 / 拒绝 / ban 状态 / 总是保持选择 | 真机 + 开发者工具 |
| 发送流程 | quota 充足 / 耗尽 / 过期 / 用户退订 | 云函数日志 + 真机接收 |
| 触发器 | 定时触发准确性 / 失败重试 / 补发 | 云函数日志 + 监控告警 |
| 频次控制 | 单日上限 / 静默时段 / 熔断 | 模拟多事件触发 |
| 字段合规 | 超长截断 / 类型不匹配 / 空值 | 单元测试 |
| 降级 | 发送失败站内消息兜底 | 故意制造 43101 错误 |
| 退订 | 偏好关闭 / 微信侧退订 / 重新授权 | 隐私中心交互 |

### 9.2 真机调试要点

1. **必须真机调试**：开发者工具无法完整模拟订阅消息授权弹窗
2. **测试号限制**：测试号无法发送真实通知，必须用正式 AppID 的体验版
3. **miniprogramState**：开发版 / 体验版 / 正式版分别对应不同状态，调试时按当前版本切换
4. **openid 来源**：云函数中 `cloud.getWXContext()` 获取的 openid 才是真实 openid
5. **模板 ID 一致性**：开发、体验、正式环境共用同一套模板 ID，不区分环境

### 9.3 灰度发布建议

| 阶段 | 范围 | 时长 | 关注指标 |
|---|---|---|---|
| Alpha | 内部 5 人 | 3 天 | 链路打通、无致命 bug |
| Beta | 100 人白名单 | 7 天 | 授权转化率、发送成功率、用户投诉 |
| GA 10% | 10% 用户 | 7 天 | 7 日召回率、退订率、负面反馈 |
| GA 50% | 50% 用户 | 7 天 | 同上 |
| GA 100% | 全量 | - | 持续监控 |

**灰度机制**：在 `notification_preference` 中加 `grayEnabled` 字段，由云函数控制是否对该用户启用通知。

### 9.4 关键指标监控

| 指标 | 目标值 | 告警阈值 |
|---|---|---|
| 授权弹窗通过率 | ≥ 50% | < 30% 告警（弹窗时机不当） |
| 发送成功率 | ≥ 98% | < 90% 告警 |
| 单用户日均接收数 | ≤ 2 条 | > 5 条告警（防骚扰失灵） |
| 用户主动退订率 | ≤ 5% / 月 | > 10% 告警（内容质量差） |
| 通知打开率 | ≥ 25% | < 15% 告警（内容不吸引） |
| 通知召回率（7 日） | ≥ 20% | < 10% 告警 |
