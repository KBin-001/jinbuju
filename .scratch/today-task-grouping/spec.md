# 今日行动智能分组：今日重点 / 快速推进 / 稍后安排

## Problem Statement

今日页的行动列表目前采用纯位置切片分组：取推荐任务或第一个任务为"优先完成"，随后 2 个为"可快速开始"，其余为"稍后处理"。这种分组方式存在三个问题：

1. **分组名不够准确**："优先完成"和"可快速开始"听起来像按钮而非任务分类；"稍后处理"带有"拖延区"的负面暗示。用户不清楚每个分组里应该放什么。
2. **没有优先级评分**：所有任务按原始顺序切片，不考虑重要程度、截止紧迫度、对目标的推动价值等因素。真正重要的任务可能被放到"稍后处理"，而不重要的任务可能占据"优先完成"位置。
3. **用户无法手动调整**：当系统分组不符合用户当下判断时，用户没有"设为今日重点""移到快速推进""稍后安排"等快捷调整入口，只能被动接受系统分组。

## Solution

将今日行动的三段式分组从"纯位置切片"升级为"系统推荐 + 用户可调"的智能分组机制。系统根据多维优先级评分自动分类，用户拥有最终决定权，可随时手动调整。具体：

- **重命名三个分组**："优先完成" → "今日重点"，"可快速开始" → "快速推进"，"稍后处理" → "稍后安排"。
- **引入优先级评分**：系统根据重要程度（35%）、截止紧迫度（25%）、对目标的推动价值（20%）、连续行动与任务依赖（10%）、用户执行习惯（10%）计算每个任务的优先分，自动分入三个组。
- **约束分组容量**："今日重点"最多 2 个，"快速推进"最多 3 个且仅收预计不超过 40 分钟的任务，依据不足时默认放入"稍后安排"。
- **用户手动覆盖**：在任务"···"菜单中新增"设为今日重点""移到快速推进""稍后安排"三个快捷操作，覆盖以 `priorityOverride` 字段持久化。
- **理由标签**：在"今日重点"任务的右侧显示推荐理由（如"推进核心目标""今天截止""已连续行动 6 天"），让用户理解为何被推荐。
- **推荐说明**："按习惯推荐"标签点击后弹出轻量说明，解释系统推荐依据并告知用户可随时调整。

## User Stories

1. 作为今日页用户，我看到行动列表的三个分组分别叫"今日重点""快速推进""稍后安排"，名称清晰中性，不会有"拖延区"的负面暗示。
2. 作为今日页用户，"今日重点"分组最多只显示 2 个任务，这样我不会被过多"重点"淹没，能聚焦当天最值得完成的事项。
3. 作为今日页用户，被放入"今日重点"的任务右侧显示推荐理由（如"推进核心目标""今天截止""已连续行动 6 天"），这样我理解系统为何推荐它。
4. 作为今日页用户，"快速推进"分组只收预计不超过 40 分钟、当前可直接执行的任务，这样我能利用碎片时间快速获得完成反馈。
5. 作为今日页用户，"快速推进"分组最多显示 3 个任务，保持轻量，不会变成第二个完整列表。
6. 作为今日页用户，"稍后安排"分组收纳指定稍后执行、条件不足或优先分较低的任务，并显示"已为你安排到专注时段"等中性提示，而非"待处理"等负面文案。
7. 作为今日页用户，系统判断依据不足时不会擅自将任务判定为"今日重点"，而是默认放入"稍后安排"，避免误判导致我失去信任。
8. 作为今日页用户，我在任务的"···"菜单中看到"设为今日重点""移到快速推进""稍后安排"三个选项，可以快速手动调整分组。
9. 作为今日页用户，我手动将任务移到某个分组后，该任务在我的调整被清除前始终留在该分组，系统不会自动覆盖我的手动决定。
10. 作为今日页用户，我手动调整分组的操作即时生效，列表立即重新排列，无需刷新页面。
11. 作为今日页用户，我连续多次将同类任务手动移到同一分组后，系统逐渐学会我的习惯，后续新建类似任务时自动分入我偏好的分组。
12. 作为今日页用户，我创建任务时可以选择"重要程度"（必须完成 / 普通任务），系统据此影响优先级评分。
13. 作为今日页用户，我创建任务时可以选择"是否阻塞其他任务"，被标记为阻塞的任务在优先级评分中获得更高权重。
14. 作为今日页用户，我点击"按习惯推荐"标签后弹出轻量说明，告知我"系统根据截止时间、预计时长和你的行动习惯自动排序，你可以随时调整"，这样我理解推荐机制并感到掌控感。
15. 作为今日页用户，当"今日重点"已有 2 个任务时，我尝试再手动设为今日重点，系统会提示我"今日重点最多 2 项，请先移出再设置"，而非静默拒绝或超限。
16. 作为今日页用户，任务完成后自动从"今日重点"和"快速推进"中移出（进入已完成状态），空出的位置由系统重新评分补充，保持分组始终反映当前最优推荐。
17. 作为今日页用户，我没有任务时看到明确的空状态和"添加任务"入口，不会看到空的三段分组框架。
18. 作为今日页用户，只有 1 个任务时，它可能出现在"今日重点"或"快速推进"中，不会出现两个空分组占据屏幕的情况。
19. 作为今日页用户，我查看历史日期时，行动列表仍按三段式展示当时已完成的任务，分组逻辑与今日一致。
20. 作为今日页用户，系统推荐分组的评分过程对我不可见，我只看到分组结果和理由标签，不会被内部数字干扰。
21. 作为今日页用户，我手动设为"今日重点"的任务在理由标签中显示"手动置顶"，与系统自动推荐的任务区分开。
22. 作为今日页用户，"快速推进"分组的提示文案为"适合现在开始"，而非"快速开始"等听起来像按钮的文案。
23. 作为今日页用户，"稍后安排"分组的提示文案为"已为你安排到专注时段"或类似中性表述，说明这些任务并非不重要，只是当前不是最佳执行时机。
24. 作为今日页用户，带有指定执行时间（提醒时间）的任务，在"稍后安排"中显示其安排的时间，让我知道何时去做。
25. 作为今日页用户，我通过快速添加面板新建任务时不强制选择重要程度和阻塞标记，默认值为"普通任务"和"不阻塞"，降低创建成本。
26. 作为今日页用户，我在行动编辑页可以修改重要程度和阻塞标记，与快速添加面板的默认值保持一致。
27. 作为今日页用户，我标记为"必须完成"的任务在优先级评分中获得更高权重，更可能被系统推荐为"今日重点"。
28. 作为今日页用户，顺延到今天的任务如果多次未完成但仍标记为"必须完成"，系统会考虑将其放入"今日重点"并显示"连续多天未完成"理由。
29. 作为今日页用户，今天截止的任务（`currentDate` 等于今天）在优先级评分中获得截止紧迫度加分，更可能进入"今日重点"。
30. 作为今日页用户，与当前目标高度相关的任务（AI 生成或标题与目标里程碑匹配）在评分中获得目标推动价值加分。
31. 作为今日页用户，我连续行动天数较长时，系统在理由标签中显示"已连续行动 N 天"，鼓励我保持节奏。
32. 作为今日页用户，我清除某任务的手动覆盖后，该任务回到系统自动评分分组，不会被永久锁定在某个分组。
33. 作为今日页用户，分组之间的视觉层次保持一致：三个分组使用相同的卡片圆角、间距和行高，仅通过色调和图标区分，不会让某个分组显得比其他更"重要"到压视。
34. 作为今日页用户，展开"查看全部任务"后，三段式分组仍然保持，不会退化成平铺列表。
35. 作为今日页用户，我在小屏幕设备上看到三段分组合理排列，不会因分组标题和理由标签导致内容溢出或按钮被遮挡。
36. 作为产品负责人，我希望分组名和评分逻辑在全项目中统一，不出现"优先完成/今日重点"混用或"快速开始/快速推进"混用。
37. 作为开发者，我希望优先级评分逻辑是一个独立的纯函数，不耦合页面渲染逻辑，可以单独测试和调优权重。
38. 作为开发者，我希望用户的手动覆盖以可选字段持久化在任务上，与现有 `ActionTask` 数据结构向后兼容，不破坏历史数据。
39. 作为开发者，我希望新增的任务字段（`importance`、`blocksOthers`、`priorityOverride`）在快速添加面板和编辑页中可选填写，默认值保证不填也不影响基础流程。
40. 作为开发者，我希望"按习惯推荐"说明弹层复用项目已有的轻量提示模式（如 `t-message` 或简易弹层），不引入新的 UI 组件库。

## Implementation Decisions

### 1. 新增 `ActionTask` 可选字段

在 `ActionTask` 接口上新增三个可选字段，向后兼容（未填时使用默认值）：

- `importance?: "required" | "normal"` — 重要程度，默认 `"normal"`。`"required"` 表示必须完成，在评分中获得更高权重。
- `blocksOthers?: boolean` — 是否阻塞其他任务，默认 `false`。标记为 `true` 的任务在评分中获得连续行动与任务依赖维度的加分。
- `priorityOverride?: "focus" | "quick" | "later" | null` — 用户手动覆盖的分组，默认 `null`（无覆盖）。非 `null` 时该任务直接进入对应分组，跳过自动评分。

这三个字段不改变现有数据存储版本（`version: 1`），作为可选字段追加在 `ActionTask` 对象上。`ManualDataStore` 结构不变。云端同步协议（`syncManualData`）天然支持新增字段，因为同步的是整个任务对象。

### 2. 新增任务优先级分组工具函数

在 `utils/taskPriority.ts` 中新增一个纯函数 `groupTasksByPriority`，替代 `pages/index/index.ts` 中现有的 `buildActionPresentationGroups`。该函数接收任务列表和上下文，返回三个分组及理由标签。

函数签名（表达决策，非最终实现）：

```
interface PriorityContext {
  today: string;
  goalTargetDate?: string;
  currentStreakDays: number;
}

interface PriorityReason {
  key: string;          // "manual_pin" | "due_today" | "streak" | "core_goal" | "blocks_others"
  label: string;        // "手动置顶" | "今天截止" | "已连续行动 N 天" | "推进核心目标" | "阻塞其他任务"
}

interface PriorityGroup {
  key: "focus" | "quick" | "later";
  title: string;         // "今日重点" | "快速推进" | "稍后安排"
  hint: string;          // "推进核心目标" | "适合现在开始" | "已为你安排到专注时段"
  icon: string;
  tone: "gold" | "green" | "muted";
  tasks: Array<Task & { priorityReasons: PriorityReason[] }>;
}

function groupTasksByPriority(tasks: ViewTask[], context: PriorityContext): PriorityGroup[]
```

评分公式（内部计算，不展示给用户）：

```
任务优先分 = 重要程度 × 35%
           + 截止紧迫度 × 25%
           + 对目标的推动价值 × 20%
           + 连续行动与任务依赖 × 10%
           + 用户执行习惯 × 10%
```

各维度评分依据：

- **重要程度**：`importance === "required"` 得满分，`"normal"` 得基准分。
- **截止紧迫度**：`currentDate === today` 得满分；`currentDate < today`（顺延/待继续）得次高分；未来任务得低分。
- **对目标的推动价值**：`source === "ai"`（AI 生成计划中的任务）得加分；标题与目标里程碑关键词匹配得加分；`estimatedMinutes` 较长的任务略加分（投入越多推动越大）。
- **连续行动与任务依赖**：`blocksOthers === true` 得满分；`rolloverCount > 0`（多次顺延但仍重要）得次高分；正常任务得基准分。
- **用户执行习惯**：用户历史上多次将同类任务手动移入某分组时，新建同类任务在该维度获得对应加分（需从 `priorityOverride` 历史记录中学习模式；初期依据不足时该维度得中性分）。

分组规则：

- `priorityOverride` 非 `null` 的任务直接进入对应分组，理由标签为"手动置顶"。
- 高优先分任务进入"今日重点"，最多 2 个；超出的降级到"快速推进"或"稍后安排"。
- 中等优先分且 `estimatedMinutes <= 40` 的任务进入"快速推进"，最多 3 个。
- 指定稍后执行（`reminder.time` 指向下午/晚上）、条件不足、或优先分较低的任务进入"稍后安排"。
- 评分依据不足时（如新建用户无历史数据），不擅自判定为重点，默认放入"稍后安排"。

### 3. 重命名 `ActionPresentationGroup`

将 `pages/index/index.ts` 中 `ActionPresentationGroup` 的 `key` 类型从 `"priority" | "quick" | "later"` 改为 `"focus" | "quick" | "later"`，`title` 改为"今日重点""快速推进""稍后安排"。`tone` 保持 `"gold" | "green" | "muted"`。`hint` 更新为"推进核心目标""适合现在开始""已为你安排到专注时段"。

### 4. `buildActionPresentationGroups` 改为委托

将 `pages/index/index.ts` 中现有的 `buildActionPresentationGroups` 改为调用 `groupTasksByPriority`，传入任务列表和从 `getProgressSummary` 获取的上下文。页面 `load()` 和 `applyTaskPatch()` 中调用 `buildActionPresentationGroups` 的位置不变。

### 5. 任务菜单新增分组操作

在 `openTaskMenu`（`pages/index/index.ts`）中，为未完成任务新增三个菜单项：

- "设为今日重点" → 设置 `priorityOverride = "focus"`
- "移到快速推进" → 设置 `priorityOverride = "quick"`
- "稍后安排" → 设置 `priorityOverride = "later"`

同时在菜单中新增"清除分组覆盖"选项（当 `priorityOverride` 非 `null` 时显示），清除后回到系统自动评分。

设为"今日重点"时需检查当前"今日重点"分组是否已满 2 个；若已满，提示"今日重点最多 2 项，请先移出再设置"。

### 6. 新增 `manualTask` 服务函数

在 `services/manualTask.ts` 中新增 `updateTaskPriorityOverride(taskId, override)` 函数，持久化 `priorityOverride` 字段。遵循现有服务层模式（读取存储 → 更新字段 → `updatedAt` → 写回存储）。

### 7. 快速添加面板与编辑页新增字段

在快速添加面板（`pages/index/index.ts` 的 `quickAdd` 相关逻辑）中新增"重要程度"选择器（默认"普通任务"）和"是否阻塞其他任务"开关（默认关闭）。二者均为可选，不填不影响保存。

在行动编辑页（`pages/action-edit/index.ts`）中同步新增这两个字段的编辑入口。

`createTask` 和 `updateTask` 的 `SaveTaskInput` 接口新增 `importance` 和 `blocksOthers` 可选参数。

### 8. 理由标签渲染

在 `today-action-list` 组件的 WXML 中，为"今日重点"分组的任务行新增理由标签渲染区域。理由标签为小号文字标签，紧跟任务标题或状态标签之后，使用克制金色（`--color-gold`）或主色低透明度变体。

### 9. "按习惯推荐"说明弹层

将 `pages/index/index.ts` WXML 中现有的 `<view class="habit-recommend">` 改为可点击元素，点击后弹出轻量说明（使用 `t-message` 或简易半屏弹层）。说明文案："根据截止时间、预计时长和你的行动习惯自动排序，你可以随时调整。"

### 10. 不引入新依赖

- 不引入新的 UI 组件库；理由标签和说明弹层复用 TDesign 已有组件。
- 不引入新的状态管理；`priorityOverride` 随任务对象存储在现有 `ManualDataStore` 中。
- 不引入新的云函数；分组逻辑在本地完成，不需要云端计算。

## Testing Decisions

### 什么算好测试

只测外部行为，不测实现细节。对于优先级分组，"外部行为"即：给定任务列表和上下文，函数返回的分组结果是否符合规则（容量限制、评分排序、理由标签、手动覆盖优先）。契约层测"页面与服务的接线约定存在且自洽"。不测私有评分函数的中间值、不测 `setData` 中间态。

### Seam 1（主，行为）— 优先级分组工具函数

新建 `tests/task-priority.test.js`，遵循项目既有的 `node:assert/strict` + TypeScript 转译 shim 模式（与 `task-status.test.js` 一致）。真实 `require()` `utils/taskPriority.ts` 模块并断言返回值。

断言覆盖：

- 空任务列表返回空分组数组。
- 单个任务只产生一个非空分组（"今日重点"或"快速推进"），不出现两个空分组。
- `priorityOverride = "focus"` 的任务直接进入"今日重点"，理由标签包含"手动置顶"。
- `priorityOverride = "quick"` 的任务直接进入"快速推进"。
- `priorityOverride = "later"` 的任务直接进入"稍后安排"。
- `importance = "required"` 的任务优先分高于 `importance = "normal"` 的任务。
- `currentDate === today` 的任务截止紧迫度得满分，比未来任务排序靠前。
- `estimatedMinutes > 40` 的任务不进入"快速推进"，即使优先分中等。
- "今日重点"分组最多 2 个任务；超出的降级。
- "快速推进"分组最多 3 个任务。
- 评分依据不足时（如无历史数据），任务默认进入"稍后安排"而非"今日重点"。
- 已完成的任务不参与优先级分组（由上层过滤）。
- 理由标签的正确性：`currentDate === today` 且高分的任务理由包含"今天截止"；`currentStreakDays >= 6` 时理由包含"已连续行动 N 天"。
- `goalTargetDate` 接近今天时，与目标高度相关的任务获得推动价值加分。

## Out of Scope

- 不重构任务状态机（pending / completed / partially_completed / skipped / rescheduled 转换逻辑不变）。
- 不修改计时会话（action session）的启动、暂停、结束逻辑。
- 不修改云端同步协议（`syncManualData` 天然支持新增可选字段）。
- 不引入任务间显式依赖图（"阻塞其他任务"仅作为评分加权标记，不建立任务间的前驱后继关系）。
- 不为"用户执行习惯"建立独立的机器学习模型；初期从 `priorityOverride` 历史频率中提取简单规则，后续可迭代。
- 不修改进度页、小队页、AI 教练对任务数据的消费方式。
- 不修改日历、热力图、连续天数等统计逻辑。
- 不修改成就系统。
- 不为分组逻辑新增云函数；所有计算在本地完成。
- 不修改 `ManualDataStore` 的 `version` 字段（新增可选字段不破坏版本兼容性）。
- 不为"今日重点"引入拖拽排序；用户通过菜单调整分组，组内顺序由评分决定。
- 不修改 `getTodayPageTasks` 的数据过滤逻辑（今日 + 待继续的任务集合不变，仅分组方式改变）。

## Further Notes

- 本特性是今日页信息架构优化，属于 P1 级体验提升，不阻塞核心功能但显著影响用户对行动列表的理解效率。
- 现有 `buildActionPresentationGroups` 函数注释明确写了"仅用于首页视觉编排：不写回任务优先级"，本特性将其升级为基于评分的智能分组，同时引入 `priorityOverride` 持久化用户手动决定——这是从"纯视觉编排"到"系统推荐 + 用户可调"的范式转变。
- `priorityOverride` 的持久化意味着即使用户退出小程序再进入，手动调整仍保留。清除覆盖后回到系统自动评分。
- "用户执行习惯"维度（10% 权重）是本特性中最不确定的部分：初期数据不足时该维度得中性分，不显著影响分组结果；随着用户使用积累，该维度逐渐生效。这符合"系统负责推荐，用户拥有最终决定权"的设计原则。
- 理由标签的文案需与 `AGENTS.md` 第 8 节文案规范一致：使用自然简洁的中文，避免空泛口号，提示与当前用户状态相关。
- 分组间的视觉层次需与 `AGENTS.md` 第 6.3 节一致：卡片圆角 24–32rpx，同级卡片保持一致，阴影轻，不使用大面积悬浮阴影。
- 风险点：`priorityOverride` 与系统自动评分的交互需明确——覆盖优先于评分，但清除覆盖后立即回到评分。需确保用户不会因"忘记清除覆盖"而导致任务永久锁定在某个分组。
- 风险点：评分公式中"对目标的推动价值"维度依赖启发式判断（AI 生成标记、标题关键词匹配），初期可能不够精准；但不精准时该维度仅占 20%，且"依据不足默认放入稍后安排"的约束兜底，不会因误判造成严重体验问题。
