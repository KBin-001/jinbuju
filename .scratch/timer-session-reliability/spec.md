# 计时会话可靠性：悬浮计时条始终可见、可结束

## Problem Statement

用户在今日页点击任务的「开始专注」后，只看到一个短暂的「开始计时」提示，底部没有出现悬浮计时条；随后找不到「结束计时」入口，计时无法停止。更糟的是，由于全局仍存在一个「运行中」的会话，用户点击其他任务的「开始专注」时会被提示「请先结束当前计时」，但屏幕上没有任何可结束的控件——形成死锁。

根因：今日页在加载数据时，用「当前激活目标的作用域任务列表」去查找活跃会话关联的任务。只要该任务被顺延、被软删除、或属于另一个目标（目标切换/激活目标 fallback），查找就落空，悬浮条因 `visible` 条件不满足而隐藏；同时「结束计时」处理函数在页面丢失会话 id 时会静默返回，既不弹窗也不给反馈。

## Solution

把「活跃会话 + 其任务」的解析下沉为服务层单一职责的能力，让悬浮计时条始终反映**全局唯一**的活跃会话，与当前选中的日历日期、当前激活目标解耦。具体：

- 悬浮计时条的可见性只取决于「是否存在运行中/暂停中的会话」，不再受日历日期或目标过滤影响。
- 活跃会话的任务按会话持有的 `taskId` 直接解析，不经过目标作用域列表，因此任务被顺延或属于其他目标时仍能锚定计时条。
- 当任务已被软删除（真正的孤儿会话），计时条不静默消失，而是进入恢复态，提供「结束并清理」入口，消除死锁。
- 「结束计时」在页面丢失会话引用时，先从全局重新获取会话再继续；确实没有会话时给出反馈，而非静默返回。
- 今日页订阅会话变更事件，会话状态在其他页面（如专注计时页）改变时即时同步。

## User Stories

1. 作为今日页用户，我点击任务的「开始专注」后，底部立即出现悬浮计时条，这样我能确认计时已开始。
2. 作为今日页用户，我正在计时某项行动，即便把日历切到其他日期查看历史，悬浮计时条依然显示，这样我随时可以回到当前计时。
3. 作为今日页用户，我计时的任务后来被「顺延到明天」，悬浮计时条仍显示该会话，这样我能正常结束并保存本次投入。
4. 作为今日页用户，我有多个目标，切换激活目标后，原先目标下正在进行计时的悬浮条依然显示，这样我不会丢失正在进行的计时。
5. 作为今日页用户，我计时的任务被删除后，悬浮计时条显示「行动已删除」并提供「结束并清理」，这样我能清除残留会话、恢复正常使用。
6. 作为今日页用户，我点击悬浮条的「结束计时」，必定弹出确认（仅结束计时 / 标记完成），不会出现点击无反应的情况。
7. 作为今日页用户，当页面因某种原因丢失会话引用时，点击「结束计时」会自动重新获取当前会话再处理，而不是静默失败。
8. 作为今日页用户，当确实没有进行中的计时时，点击「结束计时」会得到「当前没有进行中的计时」的明确反馈，而不是毫无反应。
9. 作为今日页用户，我在专注计时页（独立页面）结束或暂停会话后，返回今日页时悬浮计时条状态已同步，不需要手动刷新。
10. 作为今日页用户，我在今日页暂停/继续计时后，悬浮条的状态、文案、按钮立即更新，这样我能清楚看到当前是计时中还是已暂停。
11. 作为今日页用户，我结束计时选择「仅结束计时」后，任务进入「完成一部分」，投入时间被正确累计，悬浮条消失。
12. 作为今日页用户，我结束计时选择「标记完成」后，任务进入「已完成」，投入时间被正确累计，悬浮条消失。
13. 作为今日页用户，我在计时进行中点击其他任务的「开始专注」，若新任务与当前计时任务不同，会被提示先结束当前计时——而当前计时条确实可见、可结束。
14. 作为今日页用户，计时的「实际投入」按会话已耗时取整计算（不足 1 分钟按 1 分钟），并在结束弹窗中可修正，这样最终记录符合真实情况。
15. 作为今日页用户，退出小程序后重新进入今日页，运行中的会话按时间戳恢复已耗时，悬浮条正确显示，这样跨会话计时连续。
16. 作为今日页用户，悬浮计时条只承担计时控制，不会压过任务列表和状态信息，按钮始终可达、可点击。
17. 作为今日页用户，无论当前激活目标是什么，全局最多只有一个运行中/暂停中的会话，不会出现多个计时条互相干扰。
18. 作为今日页用户，计时相关的状态（运行中/暂停/已结束/已放弃）在今日页、专注计时页、进度页之间口径一致，不会出现一个页面显示计时中、另一个页面显示已结束的矛盾。
19. 作为今日页用户，我点击悬浮条「暂停」后会话进入暂停态，点击「继续」后恢复计时，两个操作都有即时视觉反馈。
20. 作为今日页用户，网络同步失败时，结束计时的本地保存仍成功，并提示「已保存，稍后自动同步」，不会因云端不可达而丢失本次投入。
21. 作为今日页用户，结束计时弹窗的标题、内容、按钮文案清晰，明确区分「仅结束计时（保留为完成一部分）」和「标记完成」，不会误操作。
22. 作为今日页用户，悬浮计时条在任务标题过长时合理截断，不遮挡「结束计时」按钮，保证可操作性。
23. 作为今日页用户，当活跃会话的任务属于非当前激活目标时，悬浮条仍显示任务标题（可附目标名以便识别），这样我能判断是否需要切换目标。

## Implementation Decisions

### 1. 新增服务层「活跃会话上下文」解析能力

在行动会话服务中新增一个函数（工作名 `getActiveActionSessionContext`），返回全局唯一的活跃会话及其任务，作为页面解析计时条数据的唯一入口。这把原先散落在页面 `load()` 里的、依赖目标作用域列表的查找逻辑，下沉为服务层单一职责。

返回结构（来自原型，表达决策而非完整实现）：

```
type ActiveActionSessionContext =
  | { session: ActionSession; task: ActionTask }      // 正常：会话及其任务均存在
  | { session: ActionSession; task: null }            // 孤儿：任务已被软删除
  | null;                                             // 无活跃会话
```

关键行为：
- `session` 来自现有的全局活跃会话查询（第一个 running 或 paused）。
- `task` 按会话的 `taskId` 直接从数据存储解析，**不经过目标作用域过滤**，因此 `rescheduled` 和跨目标的任务仍能解析。
- 任务被软删除时返回 `task: null`，交由页面决定恢复态展示。
- 该函数不接收、也不依赖「选中日期」参数——活跃会话是全局概念，与日历无关。

### 2. 今日页 `load()` 解耦活跃会话的读取

- 移除「仅当 `selectedDate === today` 时才读取活跃会话」的门控。悬浮计时条在任意选中日期下都应反映全局活跃会话。
- 活跃会话的任务解析改用上述服务上下文函数，不再用 `getTasksByGoal(activeGoalId).find(taskId)`。
- 今日任务列表的装饰逻辑（标记某行为「正在专注」）仍可基于会话 `taskId` 与当前列表匹配；若会话任务不在当前列表里（顺延/跨目标），列表不标红，但悬浮条仍显示——二者解耦。

### 3. 孤儿会话恢复态

当服务上下文返回 `task: null` 时，悬浮计时条不隐藏，而是进入恢复态：
- 显示极简信息（如「行动已删除」）与会话已耗时。
- 只保留一个「结束并清理」操作，调用现有的 `abandonActionSession`（不计入时间）清除残留会话。
- 恢复态不展示「暂停/继续」，因为没有可锚定的任务。

这消除了「会话存在但任务不可见」导致的死锁。

### 4. 「结束计时」不再静默失败

- `requestFinishTimer` 与 `finishActiveTimer` 在页面 `activeSessionId` 为空时，先调用服务上下文函数重新获取活跃会话；若存在则用其 id 继续，而非静默 `return`。
- 若确实无活跃会话，给出明确反馈（如 `wx.showToast`「当前没有进行中的计时」），保证按钮永远有响应。
- 保留 `timerSubmitting` 防重复提交的守卫，但其失败需有反馈。

### 5. 今日页订阅会话变更事件

- `onLoad` 中新增对 `action-session:update` 事件的订阅，回调里调用 `refreshActiveSession()`（轻量刷新）或 `load()`（全量，按变更影响面决定）。
- `onUnload` 中取消订阅，避免内存泄漏。
- 这使得从专注计时页或后台同步改变会话状态后，返回今日页时计时条即时同步，而不只依赖 `onShow → load()`。

### 6. 全局单活跃会话不变式

服务层已强制全局最多一个 running/paused 会话（`startActionSession` 遇到已有活跃会话且任务不同时抛错）。本次不改变该不变式，但规格明确：悬浮计时条始终对应这唯一的活跃会话；恢复孤儿会话后用户才能开始新计时。

### 7. 不引入新依赖、不改变数据结构

- 不修改 `ActionSession` / `ActionTask` 的字段定义。
- 不新增云函数；本地存储与云端同步流程不变。
- 不引入新的 UI 组件库；悬浮计时条复用现有 `active-timer-bar` 组件，仅扩展其数据输入与恢复态分支。

## Testing Decisions

### 什么算好测试

只测外部行为，不测实现细节。服务层测「给定输入，返回什么、状态变成什么」；契约层测「页面与服务的接线约定存在且自洽」。不测私有函数、不测 `setData` 中间态、不测无法从外部观察的内部变量。

### Seam 1（主，行为）— 服务层

扩展已有的行动会话服务层行为测试。该文件已用 TypeScript 转译 shim + 最小 `wx` 存储 mock，真实 `require()` 服务模块并断言返回值与状态，是测本特性外部行为的最高 seam。

新增断言覆盖 `getActiveActionSessionContext`：
- 活跃会话存在且任务为 `rescheduled` 时，上下文返回会话 + 该任务（验证顺延不丢失）。
- 活跃会话的任务属于非当前激活目标时，上下文仍返回会话 + 该任务（验证跨目标不丢失）。
- 活跃会话存在但任务被软删除时，上下文返回 `{ session, task: null }`（验证孤儿可识别）。
- 无活跃会话时返回 `null`。
- 全局单活跃会话不变式：已有 running 会话时，对其他任务调用 `startActionSession` 抛错。
- 顺延任务的会话结束后，任务按 `markTaskCompleted` 进入 `partially_completed` 或 `completed`，投入正确累计（回归现有 `finishActionSession` 行为在新解析路径下仍成立）。

### Seam 2（护栏，契约）— 页面接线

扩展已有的今日页计时契约测试。该文件已把页面 WXML/TS 当文本读、断言关键绑定串存在，是防止接线回归的廉价护栏。

新增断言覆盖：
- 页面通过服务上下文函数解析活跃会话任务（而非 `getTasksByGoal(...).find` 形式的目标作用域查找）。
- 页面不以 `selectedDate === today` 门控活跃会话读取。
- `onLoad` 订阅 `action-session:update`，`onUnload` 取消订阅。
- `requestFinishTimer` 在会话引用缺失时存在从全局重新获取会话的逻辑（而非直接 `return`）。
- 悬浮计时条组件的 `visible` 条件最终归结为「存在活跃会话」。

### 既有先验

两个 seam 均为项目已有测试文件，分别覆盖服务层行为与页面契约，与本特性的两层修复天然对应，无需新建测试文件、无需引入新测试框架（项目无 jest，测试以纯 `node` + `node:assert` 运行）。

## Out of Scope

- 不重构行动会话的完整状态机（running/paused/completed/abandoned 转换逻辑保持不变）。
- 不修改专注计时页（`pages/action-session`）的交互与 UI。
- 不改变投入时间的取整规则、上限（480 分钟）、或业务日期计算。
- 不引入番茄钟、通知联动、或新的计时模式（stopwatch/countdown 保持现状）。
- 不修改小队榜单、进度趋势、AI 教练对计时数据的消费方式。
- 不清理历史已完成/已放弃的会话记录（`actionSessions` 数组不裁剪）。
- 不调整云函数 `syncManualData` 的同步协议。

## Further Notes

- 本特性修复的是 P0 级死锁：用户无法结束计时、无法开始新计时，属于阻塞性问题，应优先修复。
- `BUG_20260707.MD` 中记录的 18 个历史 bug 均已修复且不含本问题，本规格是全新议题。
- 修复需保持与 `AGENTS.md` 第 5.1 节一致：完成行动后同步更新今日数据、目标进度、小队榜单和复盘统计——本次不改变这些下游更新，仅修复会话解析与计时条可见性，因此下游链路天然不受影响。
- 恢复孤儿会话使用现有 `abandonActionSession(keepTime=false)`，不引入新的会话终态。
- 风险点：解耦「选中日期」与「活跃会话读取」后，需确认非今日日期下今日摘要数字不误算入活跃会话的进行中投入（现有 `sessionMinutes` 仅在今日摘要场景叠加，需复核非今日日期下不叠加）。
